# Extension installs the CodexBar CLI on the user's behalf

When `codexbar` cannot be resolved, every command in this extension is dead, and the fix upstream intends — the CodexBar app's Settings → Advanced → Install CLI button — lives in another app the user has to context-switch into. Yet when the app is already installed, everything the fix needs (the app's bundled `Contents/Helpers/CodexBarCLI`) is sitting on disk; only a symlink in a bin dir is missing.

Decision: the extension may create that symlink itself. The unavailable-state install help forks on app presence: with the app installed (helper executable), the primary action runs `installCodexBarCli` (`src/lib/cliInstall.ts`) after an explicit confirmation dialog; without it, the view only lays out install routes — Homebrew commands or downloads — with nothing programmatic. App presence gates only which help view renders and whether the offer appears; it never gates usage. A standalone CLI install (Homebrew formula, release tarball) stays first-class, and the success path never looks for the app at all.

The routine is a faithful port of the app's own Install CLI button (`Sources/CodexBar/PreferencesAdvancedPane.swift` @ v0.45.1), not an invented installer: best-effort over both `/usr/local/bin` and `/opt/homebrew/bin` in that order, never overwriting an existing destination, never creating a missing bin dir, never escalating privileges, and reporting upstream's verbatim per-directory result strings. Mirroring the algorithm keeps the two installers indistinguishable on disk — same symlink, same destinations — so either side can later repair or recognize what the other created; `docs/upstream-parity.md` (surface 6) is the contract for keeping them identical. Success is judged only by re-running the availability gate afterwards — the linked CLI must resolve *and* pass the `--version` smoke test, the same bar `getCodexBarAvailability` applies before declaring the CLI available (resolution alone would bless a quarantined, wrong-architecture, or corrupt helper that revalidation immediately rejects) — never inferred from the status line. Filesystem paths never appear in the UI copy — the verbatim status line, joined by the launch failure when the linked CLI resolved but could not run, is exposed only through the opt-in Copy Details action.

Rejected alternatives. The repo script `bin/install-codexbar-cli.sh` escalates with administrator privileges; an extension prompting for a password to write one symlink is out of proportion and diverges from the GUI behaviour we mirror. Offering the Homebrew formula while the app is present would download a second, independently-versioned CLI that collides with the cask's own `codexbar` link. Keeping the app's Preferences as the only route costs a context switch the extension can spare — it remains the fallback, promoted to the lead option after a failed attempt.

Consequences:

- The extension writes outside its own support directory (a symlink in a system bin dir) — only after explicit confirmation, and disclosed in the README for store review.
- Partial success is a normal outcome (e.g. one prefix read-only): one working link is enough for `resolveCodexBarBinary(policy)`, and nothing retries or repairs the other prefix.
- The port is hand-maintained parity; drift is caught only by re-reading `PreferencesAdvancedPane.swift` (see upstream-parity.md surface 6), with `src/lib/cliInstall.test.ts` pinning each property against real temp dirs.
- An app present without its helper (older build) renders the no-app help rather than a setup offer that would immediately fail.
